## Rubric traceability

Where each item of the evaluation guideline is implemented, and how to show it.

### Demonstration

| Rubric item | Where | Show it |
|---|---|---|
| Intuitive, non-technical UX; foolproof | *Check leaf* page kept deliberately simple for non-technical users: one sentence of instructions, one large **Upload photo** button, the answer as one coloured label (green *Healthy*, red *Disease found*, yellow *Not sure*), confidence as a percentage, Yes / No feedback; client-side type/size checks, and a *Not sure* state with photo tips instead of a guess. Operator screens are kept off the farmer's navigation. | http://localhost:8080 |
| Free of UI errors; responsive; look and feel | `services/frontend/public/styles.css` (mobile breakpoints, accessible labels, `aria-live`, focus states); all API text escaped in `app.js` | resize the browser to phone width |
| User manual | [user_manual.md](user_manual.md), plus the in-app **Help** page | http://localhost:8080/help.html |
| Separate ML pipeline visualisation screen | **Pipeline console** (its own page, not a tab of the farmer page): stage status table, gate decision with reasons, model versions with aliases, data quality, throughput, Mermaid DAG, run history | http://localhost:8080/pipeline.html |
| Pipeline management console | Same console: filter run history by stage and status, tally of succeeded/failed runs, model registry table with deep links into MLflow; lifecycle actions via `make rollback` / `dvc repro` | console *Run history* and *Model versions* cards |
| Orchestrating the MLOps tool UIs | Console links to MLflow, Grafana, Prometheus alerts and Swagger, with ports from `config.js`; the Grafana dashboard has a pipeline row | the console's tool cards |
| Console for errors, failures and successful runs | Run history keeps every `success` and `failed` run with its error text (`reports/pipeline_runs.jsonl`); the *Status* filter shows failures only, with a running count | run S03 in the test plan |
| Pipeline speed and throughput | Items/sec per stage on the console and in Grafana; `reports/throughput.json` (Spark: 522 img/s), `data_quality.json` (276 img/s) | `make metrics` |

### Software engineering

| Rubric item | Where |
|---|---|
| Design document, HLD, architecture diagram | [hld.md](hld.md), [architecture.md](architecture.md) |
| OO or functional paradigm | Functional core plus an OO shell: [hld.md §4](hld.md#4-programming-paradigm) |
| LLD with endpoint definitions and I/O | [lld.md](lld.md); live at http://localhost:8000/docs |
| Loose coupling: UI and inference engine connected only by configurable REST | nginx → FastAPI → MLflow model server; all addresses are environment variables (`BACKEND_HOST`, `MODEL_SERVER_URL`, `API_BASE`) |
| Coding style | ruff (E, F, W, I, B, UP) + black at line length 100; enforced by the `lint` DVC stage and pre-commit |
| Logging | JSON structured logs with request id and stage fields, rotating file (`src/leafguard/common.py`) |
| Exception handling | Error hierarchy (`LeafGuardError` …), one error shape for every API error including 422 and 500, model-server failures mapped to 502/503, monitoring failures never break the pipeline |
| Inline documentation | Module, class and function docstrings throughout; comments explain *why* |
| Unit tests | 55 cases in `tests/unit` |
| Test plan, cases, report, acceptance criteria | [test_plan.md](test_plan.md) |

### AIOps implementation

| Rubric item | Where |
|---|---|
| Data ingestion / transformation pipeline with **Spark** | `validate` and `preprocess` stages (`src/leafguard/data/`), `local[4]`, `binaryFile` + `mapInPandas` |
| Data-engineering throughput and speed | `reports/data_quality.json`, `reports/throughput.json`, console, Grafana *Stage throughput* |
| CI with DVC; DVC DAG | `dvc.yaml`: `lint → unit_tests → validate → split → preprocess → train → evaluate → gate` ([pipeline_dag.md](pipeline_dag.md)) |
| Git LFS and/or DVC versioning | Git for code and small text reports; DVC for the dataset (`data/raw.dvc`, local remote) and every pipeline output: processed data, model, metrics (`dvc.lock`). Git LFS is not needed: the only binary file in git is a 36 KB chart (`reports/confusion_matrix.png`) |
| Experiment tracking: metrics, params, artifacts beyond autolog | `mlflow.autolog()` plus `log_system_metrics=True` (automatic CPU/memory/disk sampling per run), then, beyond autolog: the train/val/test split logged as an MLflow **dataset input** (lineage by digest), split counts, run.json, and manual logging of 13 params, 5 tags (git commit, dirty flag, DVC data hash, …), per-epoch metrics, test metrics, per-class F1, latency, confusion matrix, params.yaml, drift baseline, data-quality report ([lld.md §3](lld.md#3-mlflow-tracking-and-registry-interface)) |
| Prometheus instrumentation; what is monitored | Backend RED metrics, prediction mix, confidence, rejects, model errors, feedback, drift PSI, serving version; pipeline stages via Pushgateway; MLflow; host; containers ([lld.md §5](lld.md#5-metrics-interface-prometheus)) |
| All components monitored | 6 scrape targets, all `up` (E09) |
| Grafana in near real time | 5 s scrape interval; *LeafGuard overview* dashboard (20 panels + firing alerts), provisioned in the bundled Grafana or imported into an existing one (SETUP.md step 7) |
| Alerting | `monitoring/prometheus/alerts.yml`: 6 rules |
| MLflow for APIfication | `mlflow models serve models:/leafguard@champion` (model-server container) |
| MLproject for identical environments | `MLproject` + `python_env.yaml` (entry points: main, data, train, evaluate) |
| FastAPI for the UI's APIs | `services/backend/app/main.py` |
| Dockerised frontend and backend as separate services | `docker-compose.yml`: `frontend`, `backend`, `model-server`, `mlflow` plus monitoring, each with its own Dockerfile and healthcheck |

### Development guidelines 

| Guideline | Where |
|---|---|
| Rollback for failed deployments | `make rollback TO=<n>` (alias move + restart) |
| Data drift detection and retraining | PSI drift in the backend, alert rule, `dvc repro` retraining with the gate |
| Security (encryption) | Fernet-encrypted feedback images |
| Explainability | Top-3 alternatives, per-class F1, confusion matrix, human-readable drift features |
| End-to-end tests | `tests/e2e` |
